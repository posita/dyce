Expansion and recursion

Constructing an exploding dice mechanic

Explosion is a great way to illustrate use of the expand interface. One way to approximate an exploding die is to recursively re-roll and add to a running total whenever the outcome is the die’s highest. This framing is intuitive because it maps to well to how exploding dice are typically handled at the table.

We might start with something like the following:

TruncationWarning: expand: some branches with path probability < Fraction(1, 8388607) were truncated

What just happened? It appears that we went no further than eight rolls (a first roll plus up to seven explosions). Folks familiar with this domain might recognize the distribution looks mostly correct, but the counts are a bit…off. With eight rolls, we might also expect to see 48 as the largest outcome, but it’s not present. The TruncationWarning provides a clue.

The way to eliminate a branch from consideration when calling expand recursively is to explicitly return the empty histogram H({}) from our callback. (See the always_reroll_on_one example from expand’s docstring.) Our callback does not explicitly return H({}), but there are two scenarios where that is done implicitly on our behalf. The first is when a branch’s cumulative path probability falls below min_path_probability (which is what happened in our example above). And the second is when we’ve exhausted the call stack:

>>> from fractions import Fraction
>>> fair_coin = H({0: 1, 1: 1})
>>> expand(
...     naive_explode,
...     fair_coin,
...     min_path_probability=Fraction(0),
... )  # these numbers get *big*
H({0: ..., ...})

TruncationWarning: expand: some branches whose recursion depth exceeded 1000 were truncated

When either of those things happen, expand “truncates” those branches by returning H({}). Let’s take a closer look at our implementation:

6
       return result.outcome + expand(naive_explode, result.h)

For the above line, if expand returns H({}), our callback will also return H({}) for that branch. This is because adding H({}) to anything is H({}):

1
2
>>> H({}) + 1024
H({})

This explains why 48 is missing from our results above. A more illustrative case is trying to “explode” a one-sided die (d1), where no branch is “settled” before exhaustion occurs:

1
2
>>> expand(naive_explode, H(1))
H({})

How do we fix this? Great question! Thanks for asking!

It’s easy. We can check.

>>> def guarded_explode(result: HResult[int]) -> H[int] | int:
...     if result.outcome == max(result.h):
...         inner = expand(guarded_explode, result.h)
...         if inner:
...             # Only return another histogram if we weren't truncated
...             # somewhere down the line
...             return result.outcome + inner
...     # Every other case returns our current outcome
...     return result.outcome
>>> expand(guarded_explode, d6)
H({..., 19: 1296, ..., 23: 1296, 25: 216, ..., 29: 216, 31: 36, ..., 35: 36, 37: 6, ..., 41: 6, 43: 1, ..., 48: 1})

TruncationWarning: expand: some branches with path probability < Fraction(1, 8388607) were truncated

Much better.

But that’s fragile and highly domain-specific. Instead, we can take advantage of expand’s ability to pass down arbitrary keyword arguments to make our own depth counter.

>>> def guarded_explode_n(result: HResult[int], n: int = 0) -> H[int] | int:
...     if n > 0 and result.outcome == max(result.h):
...         inner = expand(guarded_explode_n, result.h, n=n - 1)
...         if inner:
...             return result.outcome + inner

>>> expand(guarded_explode_n, d6, n=3)
H({1: 216, 2: 216, 3: 216, ..., 22: 1, 23: 1, 24: 1})
>>> expand(guarded_explode_n, d6, n=0) == d6
True

Our callback is still implicitly limited by the min_path_probability parameter, but we can make that go away by setting it to Fraction(0) as we did in our recursion exhaustion illustration above. To make that the default, we create a simple wrapper:

>>> from collections.abc import Callable
>>> from typing import TypeVar
>>> T = TypeVar("T")
>>> def proper_explode_n(
...     source: H[T],
...     *,
...     n: int = 0,
...     min_path_probability: Fraction = Fraction(0),
... ) -> H[T]:
...
...     def _callback(result: HResult[T], *, n_left: int) -> H[T] | T:
...         if n_left > 0 and result.outcome == max(result.h):  # type: ignore[type-var] # zuban: ignore[arg-type]
...             inner = expand(_callback, result.h, n_left=n_left - 1)
...             if inner:
...                 return result.outcome + inner
...         return result.outcome
...
...     return expand(
...         _callback, source, n_left=n, min_path_probability=min_path_probability
...     )
>>> proper_explode_n(d6, n=3)
H({1: 216, 2: 216, 3: 216, ..., 22: 1, 23: 1, 24: 1})
>>> proper_explode_n(d6, n=0) == d6
True

The above is very nearly the implementation for dyce’s own explode_n, which includes a resolver parameter. We’ll explore that next.

Using dyce.explode_n

Let’s say we’re considering a new exploding mechanic. For the first explosion, one must roll the highest outcome on a given die. A second explosion occurs if either the highest or second highest outcome is rolled. A third explosion occurs if anything greater than or equal to the third highest outcome is rolled. Etc. We’ll never allow explosions if the minimum outcome is rolled.

>>> from dyce import explode_n
>>> def explosions_get_easier_resolver(
...     result: HResult[T], n_left: int, n_done: int
... ) -> H[T] | T:
...     return (
...         result.h
...         # Explode only maximum value if we haven't exploded yet,
...         # on [max - 1..max] if we've already exploded once, on
...         # [max - 2..max] if we've already exploded twice, etc.
...         # ...
...         if (
...             result.outcome >= max(result.h) - n_done  # type: ignore[operator,type-var] # zuban: ignore[arg-type,operator]
...             and
...             # ... but never explode on the minimum
...             result.outcome > min(result.h)  # type: ignore[operator,type-var] # zuban: ignore[arg-type,operator]
...         )
...         else result.outcome
...     )
>>> d10 = H(10)
>>> h = explode_n(
...     d10,
...     n=3,
...     resolver=explosions_get_easier_resolver,
... )

Now let’s consider a “diminishing returns” explosion mechanic, where standard polygonal dice “degrade” into their next smallest die for the next explosion. We’ll draft our resolver so that it can take a progression of dice in the form of a dict mapping the current die to the next one.

from dyce import H, HResult
from dyce.d import d4, d6, d8, d10, d12, d20

progression = {
    d6: d4,
    d8: d6,
    d10: d8,
    d12: d10,
    d20: d12,
}

def diminishing_returns_resolver(
    result: HResult[int],
    _n_left: int,
    _n_done: int,
    *,
    progression: dict[H[int], H[int]],
) -> H[int] | int:
    if result.outcome == max(result.h) and result.h in progression:
        return progression[result.h]
    return result.outcome

import sys
from functools import partial

import matplotlib.ticker as mticker

from dyce import explode_n
from dyce.viz.matplotlib import plot_ridge

ax = plot_ridge(
    *(
        explode_n(
            d,
            n=sys.maxsize,  # unrestricted recursion, since our resolver determines how deep we go
            resolver=partial(
                diminishing_returns_resolver,
                progression=progression,
            ),
        )
        for d in progression
    ),
    labels=("d6", "d8", "d10", "d12", "d20"),
    cmap="coolwarm",
)
ax.xaxis.set_major_locator(mticker.MultipleLocator(2))
ax.tick_params(axis="x", labelrotation=60)
ax.set_title("Diminishing explode mechanic for polygonal dice")
